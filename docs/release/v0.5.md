# Osverse 0.5 — DeepSeek Harness 跨平台接入

Osverse 0.5 把官方 DeepSeek Harness 纳入统一的检测、安装、启动和安全移除流程。Linux x64 与 Windows x64 可以直接使用；macOS x64/arm64 已完成同一安装契约与真实制品展开验证，会随 Osverse macOS 版启用。

## 重点变化

- “核心 CLI”新增 DeepSeek Harness：识别系统已有 `dsh`，显示真实位置和版本，并区分外部安装与 Osverse 托管安装。
- 点击安装后，Osverse 部署官方 `@deepseek-ai/dsh@0.1.0-rc.6` 和独立 Node.js 22.23.2，不要求用户预装 Node/npm，也不改全局 npm 环境。
- 安装完成后可从面板启动固定的 `dsh web`；启动前仍会重新扫描并验证文件身份。
- Osverse 托管的 Harness 可以预览并安全移除，Harness 自己的 Provider 配置、凭据和工作区默认保留。
- Windows 使用每用户命令入口和用户 PATH；Linux 使用不可变版本目录与原子符号链接，兼容 Ubuntu 20.04/22.04。

## 安装安全

- Harness 版本、Node 版本、平台制品和完整 npm lockfile 都固定在 Osverse 源码中，不静默追随 npm `latest`。
- Node 制品只从 `nodejs.org` 下载，并校验精确长度与 SHA-256。
- npm 包只从 `registry.npmjs.org` 下载，逐包校验 lockfile 中的 SHA-512 integrity。
- 不执行任何 npm `preinstall`、`install` 或 `postinstall` 脚本。
- Linux `node-pty` 原生模块在 Ubuntu 20.04 基线中预构建、固定哈希并保留 MIT 许可证；归档展开统一拒绝穿越、链接、设备文件、Windows ADS 与保留设备名。
- Harness 依赖仍进入高危漏洞、许可证与 SBOM 扫描。本次锁定图的 npm audit 与 OSV 扫描均为 0 个已知漏洞。

## Provider 配置

启动 Harness 后，请在其 Web 工作台的 Provider 设置中填写 DeepSeek API Key；兼容服务还需要服务商提供的协议、Base URL 和精确模型 ID。Harness 以只写方式把密钥保存在 `$DSH_HOME/.credentials.yaml`。Osverse 不读取或改写这份快速演进的 Developer Preview 配置。

详情见仓库中的 [DeepSeek Harness 接入指南](https://github.com/Oswald-Hao/Osverse/blob/main/docs/guides/deepseek-harness.md)。

## English summary

Osverse 0.5 integrates the official DeepSeek Harness into discovery, verified per-user installation, launch, and safe removal. Linux x64 and Windows x64 are enabled in the app; the same macOS x64/arm64 payload contract has been compiled and validated against real Node/npm artifacts for the future macOS release.

The installer pins `@deepseek-ai/dsh@0.1.0-rc.6` and Node.js 22.23.2, verifies Node by exact size and SHA-256, verifies every npm tarball against an embedded lockfile with SHA-512, and executes no npm lifecycle scripts. Provider credentials remain owned by Harness under `$DSH_HOME` and are preserved during removal.

This is a prerelease because DeepSeek Harness itself is still an upstream Developer Preview. Report ordinary bugs through GitHub Issues. Use private vulnerability reporting for security problems, and never include a real API key or private endpoint in an issue.
